AP Engine — EC2 Deployment Guide

Deploys the SAP-integrated AP 3-Way Match engine (Python / FastAPI) to the same EC2 Windows Server that runs Avagama, using the same pattern: a GitHub Actions self-hosted runner on the server, Nginx in front, and an auto-starting Windows service. Public URL: http://13.207.66.222:8090.

🐍 Python 3.12 + FastAPI 🏦 SAP NW RFC SDK 7.50 + pyrfc 🚀 GitHub Actions (self-hosted) ⚙ NSSM Windows service 🌐 Nginx → port 8090

EC2 · browser + installer▼

⚠Use 3.12 — the SAP binding pyrfc 3.3.1 has Windows builds up to Python 3.12. "For all users" matters: the GitHub runner runs as a Windows service and must find Python.

Test the network path from EC2 to SAP — request access LAST

EC2 · PowerShell▼
Test-NetConnection 65.2.76.131 -Port 3357
# Must show:  TcpTestSucceeded : True

3357 is the SAP RFC gateway of instance 57 (33 + instance number). If it says False, the SAP server does not accept connections from this EC2 — ask SAP Basis / the SAP server's AWS owner to allow 13.207.66.222 (TCP 3357) in its security group / firewall. Nothing else in this guide can work around that.

⚠Seen on this server: TcpTestSucceeded : False (ping also fails — ignore ping, AWS blocks it). Port 3357 works from the office laptop, so the SAP server only accepts known IPs.

# expected: 13.207.66.222 — the IP SAP must allow

7

Python environment + a manual test run

EC2 · PowerShell▼

7a — Create the venv and install packages (2–5 minutes)

cd E:\APEngine\app
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -r requirements-local.txt

You will see "pyrfc 3.3.1 is yanked" — expected: SAP stopped maintaining pyrfc, but this pinned version installs and works.

7b — Prove the SAP SDK loads and SAP answers

.\.venv\Scripts\python.exe -c "import pyrfc; print('pyrfc', pyrfc.__version__)"
.\.venv\Scripts\python.exe -c "import sap_connector, json; print(json.dumps(sap_connector.ping(), indent=1))"

Expected: pyrfc 3.3.1, then "ok": true, "sysid": "A4F". If not, see Troubleshooting.

ℹBefore SAP has allowed the server's IP: only the first line (pyrfc 3.3.1) can pass — that proves the SDK is installed correctly. The ping will return "ok": false with "partner '65.2.76.131:3357' not reached" after ~20 s. That is expected; carry on.

7c — Start the app by hand once

.\.venv\Scripts\python.exe -m uvicorn api.index:app --host 127.0.0.1 --port 8200

Leave it running. On the server, open a browser at http://127.0.0.1:8200 — the dashboard with a green Live SAP bar must appear. Then press Ctrl+C in PowerShell to stop it.

8

Run it as a Windows service with NSSM

EC2 · PowerShell (Admin)▼
nssm install ap-engine "E:\APEngine\app\.venv\Scripts\python.exe" "-m uvicorn api.index:app --host 127.0.0.1 --port 8200"
nssm set ap-engine AppDirectory "E:\APEngine\app"
nssm set ap-engine AppEnvironmentExtra "SAPNWRFC_HOME=C:\sap\nwrfcsdk" "PYTHONIOENCODING=utf-8"
nssm set ap-engine AppStdout "E:\APEngine\logs\ap-engine.out.log"
nssm set ap-engine AppStderr "E:\APEngine\logs\ap-engine.err.log"
nssm set ap-engine AppRotateFiles 1
nssm set ap-engine AppRotateBytes 10485760
nssm set ap-engine Start SERVICE_AUTO_START
nssm set ap-engine DisplayName "AP Engine (SAP 3-way match)"
nssm start ap-engine
nssm status ap-engine

Expected: SERVICE_RUNNING. Check it answers (first SAP logon takes a few seconds):

Invoke-RestMethod http://127.0.0.1:8200/api/sap/health
ℹThe app writes its log to E:\APEngine\logs\ap-engine.err.log (uvicorn logs to stderr — that's normal, not only errors).
9

Nginx: publish the app on port 8090

EC2 · PowerShell▼
⚠Same pattern as Avagama: do not edit nginx.conf beyond the single include conf.d/*.conf; line that Avagama already added. The AP Engine gets its own file.
# the include line must already exist (from Avagama setup):
Select-String -Path C:\nginx\nginx-1.30.0\conf\nginx.conf -Pattern "conf.d"

# copy the site file from the repo
Copy-Item E:\APEngine\app\deploy\ec2\ap-engine.conf C:\nginx\nginx-1.30.0\conf\conf.d\ap-engine.conf

# test, then reload with zero downtime for the other apps
cd C:\nginx\nginx-1.30.0
.\nginx.exe -t
.\nginx.exe -s reload

nginx -t must print syntax is ok and test is successful before you reload. If -s reload says OpenEvent("Global gx_reload_…") failed (5: Access is denied), Nginx runs as an NSSM service under SYSTEM — use nssm restart nginx instead (a ~1 s blip for the other sites).

⚠Why 8090 and not 2000? TCP 2000 is the Cisco phone-signalling port (SCCP). Office firewalls inspect it as phone traffic and drop normal web pages — the app answered on the server but browsers outside got ERR_EMPTY_RESPONSE. 8090 is an ordinary web port.

What the file does: listens on 8090, proxies everything to 127.0.0.1:8200, allows 25 MB PDF uploads, and waits up to 300 s (SAP posting and "Reset all demo cases" can be slow).

Invoke-WebRequest http://localhost:8090 -UseBasicParsing | Select-Object StatusCode
# Expected: 200

11d — Configure as a Windows service (replaces GitHub's config.cmd + run.cmd)

🚨Do not run ./run.cmd (GitHub's page shows it). It only runs while that PowerShell window stays open. --runasservice above installs the runner as a Windows service instead — it keeps running after you log off and starts by itself after a reboot.
OptionWhy
--labels ap-enginedeploy.yml asks for [self-hosted, windows, ap-engine] — this job never lands on the Avagama runners (and Avagama jobs never land here).
--runasserviceInstalls and starts the runner as an auto-starting Windows service.
"NT AUTHORITY\SYSTEM"The deploy must stop/start the ap-engine service, restart Nginx and write to E:\APEngine\app — the default NETWORK SERVICE account is not allowed to.
--unattendedNo questions asked — all answers are in the command.

The workflow: .github/workflows/deploy.yml

Repo (already added)▼

The file is already in the repo. What each step does on every push to main:

#StepWhat happens on the EC2
1Checkout codeFresh copy of the repo in the runner's _work folder
2Stop the appnssm stop ap-engine, waits until it is really stopped, kills any leftover python.exe running from E:\APEngine\app\.venv (e.g. a manual test run), and checks port 8200 is free — before anything is copied (the Python equivalent of stopping the PM2 process)
3Copy coderobocopy into E:\APEngine\app — keeps .env, .venv, logs
4Write .envFrom secret AP_ENV_FILE if set, otherwise keeps the server's file
5Python environmentCreates .venv if missing, pip install -r requirements-local.txt, checks the SAP SDK loads (import pyrfc)
5bOne-time setupCreates the ap-engine NSSM service, installs the Nginx site conf.d\ap-engine.conf (tests with nginx -t before reloading — a bad file is removed, other apps unaffected), adds the Windows Firewall rule for 8090. Each part is skipped when it already exists.
6Start the servicenssm start ap-engine (runs even if an earlier step failed, so the app comes back)
7Health checkCalls /api/sap/health; fails the run if the app doesn't answer; warns if SAP is unreachable
